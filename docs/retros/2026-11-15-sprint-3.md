## What we said

**PO:** The goal was the demo, and the demo is there. On Thursday Arita asked what was left to get to a demo state, we filed #133 to #136 the same hour, and by Friday afternoon Arita had run the whole thing in Azure. Then Arita gave us a new queue page design at 16:47 and it was built and checked by 18:20. That is the team working at its best. What worries me is the pile. Nine PRs wait, six of them are not needed for Tuesday at all, and they all change main under the three that are. Before a demo, the safest main is a quiet one. I want the merge list to say clearly which PRs belong to the demo and which can wait until after it. I also think we kept starting stories this weekend when the real bottleneck was Arita's merging, not our building. And the usage limit stopped us on Sunday morning, so we spent usage on stories that will sit for days.

**Architect:** Two things. First, the merge list. It was right about order, but every step was checked against main as it was when the PR was tested, not against main after the PRs above it in the list. That is why Arita kept writing "conflicts". We can check this before Arita does: take main, merge the PRs in list order one by one with `git merge-tree`, and see which step conflicts or which step changes a file another PR also changed. That is a small script, and the coordinator can run it every time it writes the merge list and every time Arita merges. Second, PR 128. A test that says "the newest migration is 0009" is a test about main today, not about the code. It was green on its own branch and red the moment another migration merged. The reviewer and I both read that test and missed it.

**Developer:** From my side, the most painful part was the Azure work on Thursday and Friday. We could not run the Demo workflow from the cloud, so Arita ran it, it failed, we fixed one line, Arita ran it again, and it failed one step later. That happened four times. On PR 149 the reviewer read the rest of the script for the same kind of bug and found nothing else, and the next run went through. We should have done that on the first failure. The other thing is drafts. The workflow tells us to open a draft PR early, but we cannot take it out of draft, so every draft becomes one more click for Arita, and on 12 Nov Arita had to ask whether PR 131 could leave draft. We should open the PR as a normal PR. The `status:in-progress` label already says it is not ready.

**Reviewer:** The reviews were worth it again. Some of what we caught: on PR 157 the audit copy job could write to the store before checking it was in the right mode. On PR 162 a Wise statement ARGUS could not read was dropped without an exception. On PR 160 the CI check let a switched off backup alert pass. On PR 159 a correction made only of tabs or line breaks counted as filled in. All fixed before Arita saw them. My miss is the PR 128 test that broke main. I will add a line to my checks: a test must not depend on what is on main today, such as the newest migration number or the number of files in a folder.

**Compliance reviewer:** Nothing could release a payment, and nothing put personal data outside the EU. The demo stand ins are kept apart from real data by a mode check, and on PR 157 we made sure that check runs before any write. The digest on PR 161 is sent only when the draft has no attachment, so no invoice leaves by mistake. One thing I want to name: the number of re-checks. On PR 157 review, compliance and QA each looked three times. Most of the second and third rounds were short, but each one needs a thread, and that is part of why the cap queued our threads and why the usage ran out.

**QA:** Agreed. QA often started on the same head as review, found the same things or nothing, and then had to re-test after the review fixes. On PR 157 my first pass was on 442443d, and the fixes came in fbf81c8 a minute later. If QA starts once review and compliance fixes are in, QA usually runs once. The cap makes QA wait for a slot anyway, so we lose little time. If QA then finds something, only the reviewer of that part needs a short re-check. On the demo itself: the demo data starts in shadow mode, and Arita found an empty queue on Friday. PR 156 fixes that with a switch on the page, but only once it is merged. If 154, 156 and 155 are not merged by Monday night, Tuesday runs on the steps the thread gave Arita on 13 Nov.

**Coordinator:** The pile is mine to fix. I started three stories on Saturday and three more on Sunday, when six PRs were already waiting, and I did not count the usage that would cost. I want a limit: when six or more PRs wait at `ready-for-arita`, the shift starts no new story. It updates the waiting PRs from main, runs the merge check the architect described, gets the re-checks done, and refines the next stories. About GitHub being unreachable for the digest: the digest said so and used the thread reports, which was the right fallback, but it could not tell Arita what had been merged. The digest should say the time of the newest GitHub data it has. And I put the 155 phone row question to Arita twice, it is still open, and that is fine: it does not block the demo.

**PO:** Last thing from me. Tomorrow's planning should keep the Monday night shift light: merge prep for the demo PRs, no new stories until Arita has merged them, so we keep usage for fixes Arita may need on Tuesday.

## What went well

- The demo goal is reached on main: ARGUS runs in Azure with sign in, the queue page, email pickup and the stand ins, and Arita ran it through.
- New demo stories went from idea to checked PR within hours (#133 to #136 on 12 Nov, the queue page redesign on 13 Nov).

- Reviews caught real problems before Arita: a write before the mode check, a silently dropped statement, a backup alert check that could be switched off, blank corrections that passed.

- Main was red for about a day because PR 128's tests depended on the newest migration on main.
- The Demo workflow needed four round trips with Arita, one bug at a time.
- 9 PRs wait for Arita two days before the demo, and 6 of them are not needed for it.
- The usage limit stopped the weekend shift for about 9 hours, after we had started more stories than Arita could merge.
- 5 PRs are still drafts that only Arita can move.
- Many PRs got two or three rounds of review, compliance and QA, which used threads and usage.
- The digest could not reach GitHub on two mornings.
