# Go live runbook

Things that must be done before ARGUS works on the real accounts mailbox, the real DATEV books or real Wise payments. Each item names who does it and where it was decided. Tick an item only when it is really done.

## Data Max ASP must provide

- [ ] **Partner email domain list.** Max ASP sends one list of vendors and customers with their DATEV account number and the email domain they send from, for example `muster-buerobedarf.de`. ARGUS loads it once. Afterwards the exception queue tells a person when an invoice comes from a new domain, so it can be added. Without the list every partner counts as an unknown sender, which is safe but sends more invoices to manual checks. Decided by Arita on #70 (4 Nov 2026). Arita asks Max ASP for it.

- [ ] **Mail folder list for the shadow run.** The folders the person who sorts the accounts Inbox files emails into today, and what each one holds (incoming invoices, outgoing invoices, payment reminders, other). ARGUS uses it to see what the person did with each email during the two weeks (#72). Folder names may only use letters and spaces for now. Paths start at the top of the mailbox, so a subfolder of the Inbox is written with the Inbox's own name, for example `Posteingang/Rechnungen` in a German mailbox. Arita asks Max ASP for it.

- [ ] **Approvers know what ARGUS keeps about them (#34).** Before the approver table is filled, Max ASP tells every approver and deputy that ARGUS stores their name and work email address, and logs every change to them in the audit log for ten years (GDPR Art. 13). Asked for by the compliance review of PR 175. Arita asks Max ASP to send this note.

## Checks the team runs

- [ ] **Graph paging link on the sandbox mailbox (#90).** Graph lists the Inbox 50 emails at a time. The tests use the link shape of our fake Graph and a few shapes real Graph is known to write, but only the real service shows which one it uses. Once the sandbox mailbox is connected (#65), the team puts at least 60 synthetic test emails in its Inbox and runs one sweep. Pass: the log line `Mailbox sweep: N in Inbox` shows the same number as the Inbox in Outlook, and there is no `refused Graph paging link` error. If that error shows up, it names the link's path: a developer adds that shape to `argus.intake.graph` with a test, and this check runs again before ARGUS reads the real accounts mailbox. While the link is refused, each sweep stops after the first page, so ARGUS also stops moving emails into its folders until the fix is deployed.
- [ ] Two weeks of shadow mode before ARGUS routes anything (#72). ARGUS starts in shadow mode on its own. See [docs/design/shadow-mode.md](../design/shadow-mode.md).
  - [ ] The folder list below is set as `ARGUS_SHADOW_FOLDERS` before the two weeks start.
  - [ ] After two weeks Arita opens the shadow report (`GET /intake/shadow-report`). Both lists of emails ARGUS would have sent to Other (`invoices_to_other` and `not_listed_to_other`) must be empty, and `warnings` must be empty too: a warning means a list may be empty for the wrong reason, for example because the folder list is missing or incomplete. If not, the thresholds (`ARGUS_SORTING_THRESHOLD_*`) are raised and the run goes on.
  - [ ] Arita switches to live mode with the switch on the queue page (#134), giving as reason which report it was and what it showed. The page calls `PUT /intake/mode`. Only the admin role can, and the switch lands in the audit log.

## Settings in production

- [ ] **Invoice reading is switched on in the sweep.** The sweep reads the invoices of an email only when `Sorting.invoicing` is set; it is off by default. Without it no case is opened, and the safety gates that need the invoice data (failed plausibility checks, a PDF that disagrees with its XML, an e-invoice that cannot be read safely, an unreadable document) never fire. Flagged by the compliance review of PR 108 (#71). The team sets it in the production wiring and checks it in the shadow run (#72).
- [ ] **Max ASP's own VAT IDs are set once for both sorting and reading.** `SortingConfig.own_vat_ids` and `Invoicing.own_vat_ids` hold every VAT ID Max ASP prints on documents. The sweep refuses to start when the two lists differ. If the list is empty, supplier invoices that print Max ASP's VAT ID above their own go to a person instead of opening a case (#106).

- [ ] **The sweep reaches DATEV, so invoices are matched to vendor accounts (#35).** `ARGUS_DATEV_URL` (DATEVconnect) and `ARGUS_DATEV_CLIENT` (the DATEV client, Mandant) are set for the intake jobs. Without them the sweep still opens cases, but matches none of them to a vendor account and opens no exception, so live invoices wait in Received where nobody sees them. After the first live sweep, check that the sweep log line shows `matched to a vendor` above 0, or that new cases have a vendor account on the invoices page. See [docs/design/vendor-match.md](../design/vendor-match.md).
- [ ] **The chart of accounts is right (#37, #18).** ARGUS proposes the G/L account and tax key from the vendor's booking history, and skips payments by their contra account, which depends on the chart. It assumes SKR03 (Arita's default on #18). If Max ASP books with SKR04, set `ARGUS_CHART_OF_ACCOUNTS=SKR04` for the web app and the intake jobs before the first live sweep. After the first live sweep, check on the invoices page that matched cases show a G/L account and that it matches what Benjamin would book. See [docs/design/account-proposal.md](../design/account-proposal.md).
- [ ] **The IBAN check is merged before the first live payment run (#36).** The vendor match (#35) finds a vendor by VAT ID even when the IBAN on the invoice differs, and by IBAN or name when there is no VAT ID. Only #36 blocks an invoice whose IBAN is not the one DATEV holds for the matched vendor, whichever rule matched it. No live payment run happens until #36 is merged. Asked for by the compliance review of PR 182.
- [ ] **The approver table is filled before the first live sweep (#34, #35).** Every vendor account that sends invoices needs an approver row; otherwise each of its invoices waits in the exception queue as "The vendor has no approver".

- [ ] **Who may send Wise statements, and which balances Max ASP holds (#56).** `ARGUS_STATEMENT_SENDERS` holds Benjamin's address (and anyone else Arita names), `ARGUS_WISE_BALANCES` every Wise balance currency, for example `EUR,USD`, and `ARGUS_REMINDER_FORWARD_TO` must be set, because the statement notices go to that address. Without `ARGUS_STATEMENT_SENDERS` only the agreed folder counts (`ARGUS_STATEMENT_FOLDER`, default `ARGUS/Kontoauszüge`). See [docs/design/bank-import.md](../design/bank-import.md).
- [ ] **The statement folder exists (#166).** In live mode the sweep creates `ARGUS/Kontoauszüge` itself. In shadow mode ARGUS creates no folders, so if people should already use it during shadow mode, Arita creates it by hand in the accounts mailbox under `ARGUS`.
- [ ] **No mailbox rule moves mail into the statement folder (#166).** Everything in `ARGUS/Kontoauszüge` is imported with no sender check, so an Outlook rule such as "mail from Benjamin goes to Kontoauszüge" would import a forged outside email with his address. Arita checks the rules of the accounts mailbox once and confirms none targets that folder. ARGUS's own filing never moves mail there.
- [ ] **Only statement emails go into the statement folder (#166).** Everything in it is stored in the 10 year locked store, so staff drop only Wise statement emails there (GDPR data minimisation). An email there without a CSV file opens an exception.
- [ ] **Mailbox auditing records moves (#166).** ARGUS cannot see who moved an email into the statement folder. Max ASP's IT confirms that mailbox auditing on the accounts mailbox records `Move` and `MoveToDeletedItems` for owners and delegates, and how long Purview keeps that log, so the person can be found later.
- [ ] **A real statement email from Benjamin is tried once (#166).** Benjamin sends one statement to the accounts mailbox. If it is imported, his emails pass the strict sender check. If it lands in the exception queue with "Absenderprüfung nicht bestanden", mail from inside the tenant carries no SPF, DKIM or DMARC result for his domain; then his statements are imported by moving each email into `ARGUS/Kontoauszüge`, and a person closes the exception in the queue with a reason. Either way works; this check only tells Benjamin which one to expect. `ARGUS_STATEMENT_SENDERS` is set in demo mode only so far; passing it in live through the deploy goes with #167.
- [ ] **Max ASP's domain publishes a strict DMARC policy (#56).** Its DMARC record has `p=quarantine` or `p=reject`, so Exchange marks an outside email that forges a Max ASP address, such as Benjamin's, as failed. Arita checks it with Max ASP's IT. Asked for by the compliance review of PR 162.
- [ ] **Only finance staff can drop emails into the statements folder (#56).** The folder `ARGUS/Kontoauszüge` has no sender check by design, so anyone with access to the accounts mailbox can feed a statement. Arita confirms with Max ASP who has access to that mailbox and that it is finance staff only.
- [ ] **The first Wise statement of each balance is checked by a person (#56).** The first imported month of a currency has nothing to compare its opening balance with, so it becomes the starting point. Benjamin compares its opening balance with Wise once.

- [ ] **The daily digest, the reminder forward and the statement notices go to Benjamin** (#167, #61, #27, #56). Arita sets these as GitHub **secrets** (Settings, Secrets and variables, Actions, tab **Secrets**). They are not credentials, but they are personal data: a secret shows as `***` in every run log, a variable would be printed in every step header. They never go in the repository, and the deploy stops while one of them is stored as a variable:
  - `ARGUS_DIGEST_TO`: Benjamin's address, exactly one. The daily email with every open exception goes there (EX-03).
  - `ARGUS_REMINDER_FORWARD_TO`: Benjamin's address, exactly one. Payment reminders are forwarded there, and the notices about a missing or blocked Wise statement go there too (BA-08).
  - `ARGUS_STATEMENT_SENDERS`: Benjamin's address, plus anyone else who may email Wise statements, comma separated. May stay empty: then only the statement folder counts.

  Who gets the exception digest and the payment reminders, and who may send statements, is a control, but GitHub keeps no history of variable changes. So Arita notes every change of these three secrets as a comment on #167 (or the go live issue that follows it): who changed which secret, when and why, never the address itself. Asked for by the compliance review of PR 178.

  Set them **before** `demo` is switched to `false` in `infra/main.bicepparam`. The deploy passes them into the scheduled jobs (`notifySettings` in `infra/main.bicepparam`); in demo mode the jobs keep the synthetic `.example` addresses. With demo off, the CI check "Infrastructure code" fails while `ARGUS_DIGEST_TO` or `ARGUS_REMINDER_FORWARD_TO` is empty or holds more than one address, so the pull request that switches demo off stays red until both are set. If one is removed later, the digest job logs `argus-job failed digest` with the reason `set ARGUS_DIGEST_TO`, sends nothing, and its alert emails Arita; without `ARGUS_REMINDER_FORWARD_TO` payment reminders wait in the Inbox. The Exchange scope of the ARGUS app must let it send from the accounts mailbox, which the reminder forward needs anyway.
