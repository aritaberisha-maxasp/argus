# 0009: Demo mode with stand ins in Azure

Status: proposed
Requirements: IN-01, NF-01, NF-04, NF-06

Issue #124. Builds on ADR 0001 (Azure, PostgreSQL, the locked document store), ADR 0003 (the mailbox), ADR 0004 (Wise) and the deploy pipeline from #81.

## Context

Arita wants to show Max ASP everything ARGUS does so far, live in Azure, before the real mailbox, DATEV and Wise are connected. Afterwards only plugging in the real systems should be left (Sprint 3 planning, 10 Nov 2026).

We already have stand ins: the fake Microsoft Graph with a mailbox (`standins/graph`), the fake DATEV (`src/argus/datev/fake.py`) and the Wise stand in (`standins/wise`). They run in CI today, not in Azure.

What constrains us:

- ARGUS lives in Max ASP's existing Azure subscription, in one resource group with one database server and one document store.
- The document store is locked: every file stays 10 years and nobody can delete it (ADR 0001). Demo emails written there would stay for 10 years.
- The audit log and the email records refuse deletes, even for the owner (ADR 0005). Demo rows in the real database could not be cleaned out before go live without switching those guards off.
- A demo must never reach a real system, and a live ARGUS must never quietly talk to a stand in. A Wise stand in must never be able to fund or release a payment (NF-04).

## Options

1. **Demo data in the real database and the real document store, wiped before go live.** Pro: nothing extra in Azure. Con: demo files stay in the locked store for 10 years, and wiping the real database means code that can empty the audit log.
2. **A second resource group for the demo.** Pro: complete separation. Con: a second copy of every Azure resource, a second deploy identity and pipeline, about double the cost, and it does not prove the real setup works.
3. **Demo mode in the real resource group, with its own database and document store.** The stand ins run as container apps next to ARGUS. ARGUS works in a database `argus_demo` on the same server and in a small storage account without a lock. The real database and the locked store stay empty until go live.

## Decision

Option 3.

- **One switch.** `demo` in `infra/main.bicepparam`. It is on while the demo comes first. It sets `ARGUS_DEMO=true` and the stand in addresses on the app, points the app at `argus_demo`, gives it the demo document store, and deploys the stand ins.
- **Settings only.** ARGUS reads where Microsoft 365, DATEV and Wise are from settings (`src/argus/connections.py`). Moving to the real systems is a settings change, not a code change.
- **The two worlds never mix.** ARGUS refuses to start when demo mode is on and a real address (https) or a real secret is set, or when demo mode is off and a stand in address (plain http to a host without a dot) or a stand in token is set. `tools/check_infra.py` refuses demo mode together with `manualSecrets` already in CI.
- **Stand ins inside the environment only.** One image, `argus-demo` (`docker/demo/Dockerfile`), holds all three stand ins and the synthetic fixtures. Three container apps run it, each with its own command, with internal ingress: no public address. Their tokens are generated by the templates and kept in Key Vault like every other secret. The Wise stand in has no funding or release endpoint, as before.
- **Seed and reset.** `python -m argus.demo seed` puts ten synthetic fixture emails into the fake mailbox. It runs as the Container Apps job `caj-argus-demo-seed`, inside the environment. `python -m argus.demo reset` rebuilds the demo database and empties the demo document store. It runs in the Demo workflow (`.github/workflows/demo.yml`) on a GitHub runner as the database admin, like the migrations, and the workflow then restarts the stand ins, which keep everything in memory. Reset refuses when demo mode is off, when the database name does not end in `_demo` and when the store's name does not contain `demo`.
- **Real AI.** The demo uses the real Azure OpenAI and Document Intelligence accounts in the EU. Only synthetic emails reach them.

## Consequences

- The real database and the locked store are untouched by the demo. At go live nothing needs cleaning, only switching (docs/runbooks/go-live.md).
- The deploy builds and pushes one more image on every merge, about a minute more per run.
- While demo mode is on, the deploy migrates and smoke tests `argus_demo`, not `argus`. The real database is migrated at the first deploy after demo mode is switched off.
- Three small always on container apps and a storage account cost a few euros a month while the demo runs. They stay until someone deletes them: switching demo mode off does not remove them, since the pipeline never deletes resources. The go live runbook lists them.
- The stand ins and the seed job run as the app identity, which can read every Key Vault secret. That is fine while the vault holds no real secret, so the go live runbook deletes them before the first real secret goes in. A separate identity for them would need Arita to widen the deploy identity's role rule (docs/operations/deploy.md, step 5), which is not worth it for a few weeks of demo.
- The reset needs the database admin, so it runs from GitHub, not inside Azure. The rows it drops are synthetic, so the GitHub log may show them; real rows never pass through it.
- Long term backups (#82) of the server also hold `argus_demo`. It holds synthetic data only, so that is harmless, and the database is dropped at go live.
- Signing in to ARGUS (#23) and the sweep job (#125) build on the same settings. The sweep calls `connections_from_env()` and never looks at the mode itself.
